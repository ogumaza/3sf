3SF 1.1.0 renders ahead during playback for instant seeking within buffered audio.
3SF rips Nintendo 3DS sequenced music into a PSF-family format, and plays it with the game's DSP
firmware on an emulated Teak DSP. It comes with a ripper (`3sfrip`), a renderer (`3sfplay`) and a
foobar2000 component. The format is described in `docs/3sf.md`.

## Downloads

| File | Contents |
|---|---|
| `3sf-1.1.0-win-x64.zip` | `3sfrip` and `3sfplay` for 64-bit Windows |
| `3sf-1.1.0-win32.zip` | `3sfrip` and `3sfplay` for 32-bit Windows |
| `foo_input_3sf-1.1.0.fb2k-component` | the foobar2000 component, for 64-bit and 32-bit foobar2000 v2 |

The programs run on Windows 10 or later and need no runtime DLLs. To install the component, open
the file with foobar2000, or add it under Preferences › Components. For other systems, see the
README for instructions on building from source.

## New in 1.1.0

- **Rendering ahead.** During playback, the foobar2000 component renders the track on a separate
  thread as fast as the CPU allows and buffers the audio. Seeking within the buffer is instant;
  seeking further ahead waits for rendering to reach the requested position. The buffer holds up
  to 10 minutes and 10 seconds of audio (about 76 MiB), enough for the longest track `3sfrip`'s
  length analysis produces. Longer tracks also save the emulation state every 2 seconds, as in
  1.0.0, for quick seeks back before the buffered audio. Rendering ahead keeps one CPU core busy
  until it reaches the end of the track or the buffer limit. To turn it off, go to Advanced
  preferences › Decoding › 3SF decoder.

## Fixed in 1.1.0

- The foobar2000 component plays rips from inside a zip or another archive when their files are
  at the archive's top level. It used to look for the `.3sflib` next to the archive.
- When `3sfrip` rips a game in archive mode and one of its sound archives can't be read or
  ripped, it rips the others and then exits with an error. It used to stop at that archive.
- The 32-bit `3sfrip` runs at most 8 length analyses at once unless `--jobs` asks for more, so
  that it doesn't run out of memory on PCs with many CPU threads.

## Features

- **Ripping.** `3sfrip` rips a decrypted 3DS game (`.3ds`, `.cci`, `.cxi` or `.cia`, or an
  extracted game folder) or a sound archive (`.bcsar`, with a DSP firmware file) into a
  `.3sflib` and a `.mini3sf` for each sound. A game's rips carry its own DSP firmware, whether the
  game stores it in a file or in its code. `3sfrip` plays each sound to determine its length
  and fade tags. It also supports drag and drop.
- **Two rip modes.** Game mode runs the game's sound code, so the rips play as the game does.
  It needs a driver profile for the game, and Pokemon X (Japan) has the only one so far. Archive
  mode plays a sound archive from any game with 3SF's model of the SDK's sound player.
- **Rendering.** `3sfplay` renders rips to WAV or FLAC at the DSP's native 32,728 Hz.
- **foobar2000.** The component plays `.3sf` and `.mini3sf` files using their length and fade
  tags. It supports tag editing, ReplayGain, endless playback and quick seeking.
- **Speed.** On 64-bit Windows, the DSP firmware is translated into x86-64 code as it plays. The
  32-bit programs interpret the firmware, which is slower, so use the 64-bit component if your
  foobar2000 and its other components allow it.

## Known limitations

- Seeking ahead of the audio buffer waits for rendering to reach the target, so a long seek
  soon after a track starts can still be slow.
- Game mode only has a profile for Pokemon X (Japan). Other games rip in archive mode, whose model
  comes from Pokemon X, so a game with another version of the sound library may play
  differently from the console.
- Only sequences are ripped. Use tools such as vgmstream for BCSTM and AAC streams. Wave sounds
  and sequences with data outside the sound archive are skipped.
- The output is stereo.
