3SF 1.3.0 adds an XMPlay plugin. The rest of 3SF is unchanged from 1.2.1.

3SF rips Nintendo 3DS sequenced music into a PSF-family format. The rips play with the game's DSP firmware on an emulated Teak DSP. 3SF comes with a ripper (`3sfrip`), a renderer (`3sfplay`), a foobar2000 component and an XMPlay plugin. The format is described in `docs/3sf.md`.

## Downloads

| File | Contents |
|---|---|
| `3sf-1.3.0-win-x64.zip` | `3sfrip` and `3sfplay` for 64-bit Windows |
| `foo_input_3sf-1.3.0.fb2k-component` | the foobar2000 component, for 64-bit and 32-bit foobar2000 v2 |
| `xmp-3sf-1.3.0.zip` | the XMPlay plugin, for XMPlay 3.8.2 or later |

The programs run on Windows 10 or later and require no runtime DLLs. To install the component, open the file with foobar2000 or add it under Preferences › Components. To install the XMPlay plugin, unzip `xmp-3sf-1.3.0.zip` and put `xmp-3sf.dll` in XMPlay's folder, or in a folder inside it. Then restart XMPlay. For macOS, see the README for instructions on building from source.

## New in 1.3.0

- **XMPlay.** The XMPlay plugin plays `.3sf` and `.mini3sf` files using their length and fade tags. The tags show in XMPlay. The `game` tag becomes the album, and `year` the date. XMPlay's Message window lists the other tags. The plugin's options page sets the default length and fade, endless playback and rendering ahead. During playback, the plugin renders ahead on a separate thread. Seeking within the buffered audio is instant. XMPlay is a 32-bit program. The plugin is therefore a 32-bit DLL. Like the 32-bit component, it interprets the DSP firmware.

## Features

- **Ripping.** `3sfrip` rips a decrypted 3DS game (`.3ds`, `.cci`, `.cxi` or `.cia`, or an extracted game folder) or a sound archive (`.bcsar`, with a DSP firmware file) into a `.3sflib` and a `.mini3sf` for each sound, or only the music with `--bgm`. A game's rips contain the DSP firmware that the game uses. The firmware can be in a file or in the game's code. `3sfrip` plays each sound to determine its length and fade tags. It also supports drag and drop.
- **Two rip modes.** Game mode runs the game's sound code. Game-mode rips play as the game does. Game mode requires a driver profile for the game. Pokemon X (Japan) has the only one so far. Archive mode plays a sound archive from any game with 3SF's model of the SDK's sound player.
- **Rendering.** `3sfplay` renders rips to WAV or FLAC at the DSP's native 32,728 Hz.
- **foobar2000.** The component plays `.3sf` and `.mini3sf` files using their length and fade tags. It supports tag editing, ReplayGain, endless playback and quick seeking. During playback, the component renders ahead. Seeking within the buffered audio is instant.
- **XMPlay.** The plugin plays `.3sf` and `.mini3sf` files using their length and fade tags. It supports endless playback. Like the component, it renders ahead during playback.
- **Speed.** On 64-bit Windows, the DSP firmware is translated into x86-64 code during playback. The 32-bit component and the XMPlay plugin interpret the firmware. Interpreting is slower. Use the 64-bit component if your foobar2000 and its other components allow it.

## Known limitations

- Seeking ahead of the audio buffer waits for rendering to reach the target. A long seek soon after a track starts can still be slow.
- Game mode only has a profile for Pokemon X (Japan). Other games rip in archive mode. Archive mode's model comes from Pokemon X. A game with another version of the sound library may play differently from the console.
- Only sequences are ripped. Use tools such as vgmstream for BCSTM and AAC streams. Wave sounds and sequences with data outside the sound archive are skipped.
- The output is stereo.
